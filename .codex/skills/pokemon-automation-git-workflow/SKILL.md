# pokemon_automation Git / GitHub 運用

- GitHub 操作は `AGENTS.md` に従い、`source "$(git rev-parse --show-toplevel)/scripts/gh-wrappers.bash"` の後、このリポジトリには `ghp`、他リポジトリの参照には `ghw` を使う。認証エラー時に別の認証へ切り替えない。
- 変更に応じて Python / Arduino の既存テストや CI 設定、`Taskfile.yml` を確認し、適切な検証を実行する。文書のみの変更では `git diff --check` を確認する。

## 着手前

- リポジトリルートの `AGENTS.md` があれば読み、`git status` と `git log --oneline -10` で作業状態と履歴を確認する。既存の未コミット変更を保護する。
- GitHub にアクセスできる場合は既存の Issue / PR を数件確認し、粒度と文体を把握する。リポジトリ名や Issue 番号を推測しない。

## 共通の書き方

- Issue、PR、コミットメッセージは日本語で書き、パスやコマンドなどの識別子はバッククォートで囲む。
- 短い見出しと箇条書きを基本に、事実と判断理由を書く。未実施の作業や検証を完了と書かない。
- 根拠となる仕様や文書がある場合は、その場所を示す。利用者から見える変更や意図的に残した課題は、該当する場合に明記する。

## Issue とブランチ

- 新規の独立したタスクは、リモートを取得して最新の `origin/main` から作業ブランチを作る。現在のブランチを起点にするようユーザーが指定していなければ、無関係な変更を引き継がない。
- 既存 PR の修正・同じタスクの継続は、その作業ブランチを使う。依存する未マージ変更が必要な場合は依存元のブランチを起点にできる。会話と差分から判断し、通常の起点選択について毎回確認を求めない。明示された起点やブランチ指定を優先する。
- 別タスクの未コミット変更がある場合は、別 worktree などで保護して作業する。選んだ起点と分離方法を簡潔に伝える。
- Issue のタイトルは「〜する」で終わる動詞句を基本とする。本文には `## 目的`、`## 内容` を書き、必要なら利用者から見える変更、対象外の作業、親子 Issue を示す。
- Issue がある場合のブランチ名は `<type>/<issue番号>-<英語の短い説明>`、ない場合は番号を省く。`type` は `feat`、`fix`、`refactor`、`test`、`docs`、`chore` を基本とする。既存の作業ブランチとユーザーの指示を尊重する。

## コミット

- `<type>(<scope>): <日本語の要約>` を基本とし、scope は変更領域に合わせる。必要に応じて本文に理由と変更点を記載する。
- 関連 Issue があれば `Refs #番号` を使い、Issue を閉じる指定は PR に記載する。異なる Issue や無関係な変更を一つのコミットに混ぜない。
- コミット前に変更に適した検証を行い、実行できなかった検証は報告する。

## Pull Request

- base はユーザーの指定を優先し、指定がなければリポジトリの既定ブランチと既存の運用を確認する。タイトルはコミットと同じ形式で、PR 全体の変更を表す。
- 本文には変更の目的、変更内容、実際の検証結果を記載する。ユーザーから見える変更や意図的に残した課題は、ある場合に別節で記載する。関連 Issue を閉じる場合は `Closes #番号` を記す。親 Issue を不用意に閉じない。
- 本文は改行を保てる `--body-file` 等で渡す。作成後は CI の結果を確認し、失敗や未確認事項を報告する。PR の作成依頼をマージの許可とみなさない。

```markdown
## 概要

変更の目的と背景、必要に応じて根拠となる文書。

Closes #番号

## 変更内容

- 変更点と、必要に応じてその理由

## 利用者から見える変更

- 該当する場合に記載

## 残課題

- 意図的に残したものと理由があれば記載

## 検証

- 実行したコマンドと実際の結果。未実施の検証があれば理由
```

## 完了報告

作成した Issue / PR の番号と URL、コミットや push の有無、検証結果、残課題を必要に応じて報告する。
